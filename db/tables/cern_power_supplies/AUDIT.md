## No type tail (by design)
- [x] A grab-bag of vendor AC-DC / DC-DC power bricks (TRACO POWER 54, XP POWER 13,
      MEAN WELL 9, ISEG, HAMAMATSU, RECOM, TDK-LAMBDA, MYRRA, …) with module-named
      symbols/footprints. `Component Type` is uniformly `Standard` and `Case` is
      blank for all but one row, so there is no clean column giving a `supply_type`
      and free-text V/W parsing was deliberately avoided. No type-specific tail —
      a legitimate outcome, same as cern_dc_dc_converters / cern_transformers.

## 3D model coverage
- [x] 1/110 (0%) — **expected**. These are brick/encapsulated/chassis vendor power
      modules with bespoke CERN footprints (`PWS_<vendor>_<series>`); KiCad ships no
      generic 3D models for them, so they go to the human drop-folder under
      `kicad_3dmodels/`. The lone covered part resolves via a footprint shared with
      another table's mapping. No new 3D mapping rules added. Not a regression
      (cf. cern_dc_dc_converters 0%, cern_transformers 0%).
- [x] `model_map.resolve_from_footprint` last-resort scan tightened: a pure-digit
      chip key (0402/0603) must be bounded by non-digits, else a vendor MPN digit
      run mis-matches it. Surfaced here by `PWS_HAMAMATSU_C11204-02` ('...04-02'
      → spurious `D_0402` diode model); the same guard also corrected three latent
      SAMTEC `SSW-104-02` mis-maps to their correct PinSocket models. Locked by
      `tests/test_model_map.py::test_chip_size_token_needs_digit_boundary`.
