* Terra EDA Library: HTTP Library Architecture

** Motivation

KiCad is slow to load very large sets of libraries. The Terra db lib is large
and will grow, as parts are added by script.

KiCad HTTP libraries (=.kicad_httplib=, KiCad 8+) solve this naturally:
they enumerate only *categories* (libraries) until expanded, then fetch
parts within a category on demand. Full part data is fetched only when a
part is selected. Search operates only over expanded categories.

This lazy-loading model eliminates the need for tier-based filtering or
SQL views. Instead, the library is split into fine-grained categories
(e.g. "SMT Resistors / 0603 / Thick Film") so each category stays small
(50–200 parts). Every part is discoverable — just organized, not hidden.

** Schema Changes

*** Tier and Tags Columns (core fields on all part tables)

Added to every =*_0_schema.sql= after =dump_priority=:

#+begin_src sql
tier INTEGER DEFAULT 0,
tags TEXT DEFAULT '',
#+end_src

- =tier=: integer, 0 = most important. Lower numbers load first.

- =tags=: comma-delimited string (e.g. ="passive,precision"=).
  Redundant with the =tags= table, but provides a migration path
  for when KiCad implements lazy loading and the join table can be
  phased out.

*** Tags Table (many-to-many, built by generators)

Created by a new schema file loaded before any part tables:

#+begin_src sql
DROP TABLE IF EXISTS tags;
CREATE TABLE tags (
    unique_id TEXT NOT NULL,
    tag TEXT NOT NULL,
    PRIMARY KEY (unique_id, tag)
);

-- selection-direction index: given tag → unique_ids
CREATE INDEX IF NOT EXISTS idx_tags_tag_uid ON tags(tag, unique_id);
#+end_src

Generators emit INSERT statements into this table alongside part INSERTs.
Each part can have multiple tags. Tags are lowercase, hyphen-separated
(e.g. =analog=, =high-rel=, =ttl=, =interface=).

*** User Tags Table (project-specific; stored in project DB)

Project SQL input file: =${KIPRJMOD}/terra_tags.sql=

The project DB contains the table (even if empty):

#+begin_src sql
DROP TABLE IF EXISTS user_tags;
CREATE TABLE user_tags (
    unique_id TEXT NOT NULL,
    tag TEXT NOT NULL,
    PRIMARY KEY (unique_id, tag)
);

CREATE INDEX IF NOT EXISTS idx_user_tags_tag_uid ON user_tags(tag, unique_id);
#+end_src

The file can populate it, e.g.:

#+begin_src sql
BEGIN TRANSACTION;
INSERT INTO user_tags VALUES ('Samsung-CL10A104KA8NNN', 'project-alpha');
-- ...
COMMIT;
#+end_src

- Can be tracked in git.
- A future KiCad plugin can provide UI for selecting parts from BOM and
  generating this file.

*** Tier + Active Tag Config Tables (project-controlled; stored in project DB)

Project SQL input file: =${KIPRJMOD}/terra_config.sql= (gitignored)

#+begin_src sql
DROP TABLE IF EXISTS terra_tier_config;
CREATE TABLE terra_tier_config (
    tier_level INTEGER NOT NULL
);

DROP TABLE IF EXISTS terra_tag_config;
CREATE TABLE terra_tag_config (
    tag TEXT NOT NULL PRIMARY KEY
);

-- Example config:
INSERT INTO terra_tier_config VALUES (3);

BEGIN TRANSACTION;
INSERT INTO terra_tag_config VALUES ('analog');
INSERT INTO terra_tag_config VALUES ('passive');
COMMIT;
#+end_src

- =terra_tier_config=: one row, sets the active tier cutoff.
- =terra_tag_config=: one row per active tag name.
- Gitignored.
- If the file does not exist (or is empty), behavior must be:
  default tier cutoff and no active tags.

** Tier Assignments

*** Tier Definitions

| Tier | Meaning               | Contents                                       |
|------+-----------------------+------------------------------------------------|
|    0 | Daily driver / curated | E96 1% 0603+0805 resistors, E12 caps in        |
|      |                       | common dielectrics/sizes/voltages, ALL static   |
|      |                       | (hand-curated) parts                            |
|    1 | Common passives       | E96 1% in 0402+1206, E12 caps in 1206/1210     |
|    2 | Extended passives     | E96 1% in 0201/2512, non-E12 or >50V caps      |
|    3 | Specialty SMT         | Thin film resistors, C0G caps (KEMET+Samsung)   |
|    4 | Deep catalog          | Y5V caps, 1812 case size                        |
|    5 | Schema default        | Fallback for tables without generator assignment |

The default tier cutoff (=DEFAULT_TIER= in Makefile) is *2*, so tiers
0+1+2 are visible by default. Tier 3+ requires explicit config or tags.

*** Per-Generator Tier Rules

**** run_200 — Yageo RC thick film resistors (~9,600 parts)

Tier is determined by package size alone. All E-series values (E24 and
E96) within a package get the same tier — no E24/E96 split.

| Condition                         | Tier |
|-----------------------------------+------|
| 0603 or 0805 (any value incl 0Ω) |    0 |
| 0402 or 1206 (any value incl 0Ω) |    1 |
| 0201, 2512 (any value incl 0Ω)   |    2 |

**** run_210 — Yageo RT thin film resistors (~46,500 parts)

All thin film → tier 3 (specialty/precision). No size differentiation;
thin film is already a niche choice.

**** run_300 — KEMET C0G MLCC caps (~7,200 parts)

All C0G → tier 3. C0G is specialty (precision/RF/low-loss).

**** run_400 — Samsung CL MLCC caps (~2,500 parts)

Tier depends on dielectric, whether the value is in the E12 series,
case size, and voltage.

| Condition                                     | Tier |
|-----------------------------------------------+------|
| E12 value, X7R/X5R, 0402/0603/0805, ≤50V     |    0 |
| E12 value, X7R/X5R, 1206/1210, ≤50V          |    1 |
| E12 value, X7R/X5R, any size, >50V            |    2 |
| Non-E12 value, X7R/X5R                        |    2 |
| C0G dielectric (Samsung)                      |    3 |
| Y5V dielectric                                |    4 |
| 1812 case size                                |    4 |

E12 detection: check if the capacitance value's mantissa matches
{1.0, 1.2, 1.5, 1.8, 2.2, 2.7, 3.3, 3.9, 4.7, 5.6, 6.8, 8.2}.

**** Static parts (all other tables)

Schema default is changed from 5 to 0, so hand-curated parts (diodes,
ICs, MOSFETs, LEDs, etc.) are always in tier 0.

**** Through-hole (resistors_th, capacitors_th)

Currently empty. When populated, mirror SMT tiers with common values
at tier 3 and unusual at tier 4.

** Default Tags

Generators assign tags based on component type and characteristics:

| Tag         | Applied to                              |
|-------------+-----------------------------------------|
| =passive=   | Resistors, capacitors, inductors        |
| =analog=    | Op-amps, analog ICs, precision parts    |
| =digital=   | Logic ICs, microcontrollers, memory     |
| =interface= | Connectors, interface ICs               |
| =ttl=       | TTL-family logic ICs                    |
| =power=     | MOSFETs, drivers, voltage regulators    |
| =precision= | Thin film resistors, C0G caps, 1% tol   |
| =vintage=   | Legacy/obsolete parts kept for ref      |

Tags are not mutually exclusive. A thin-film resistor might be tagged
=passive,precision=.

** KiCad .kicad_dbl Integration

The =.kicad_dbl= must point to the *project DB*:

- DSN: =${KIPRJMOD}/terra_local.db=
- The generator references SQL *views* (=*_v=) rather than raw tables.

Rationale:
- KiCad queries a single SQLite DB file.
- Per-project tuning is achieved by rebuilding =terra_local.db= from a
  master DB plus small SQL deltas (tier and tags).

*** Approach: SQL Views (fast and robust)

Key refinements:
- Avoid correlated per-row =EXISTS( UNION ALL ... )= where practical.
- Ensure tier cutoff never evaluates to NULL (empty config must not blank
  the library).

Define a helper view to compute included IDs from active tags:

#+begin_src sql
CREATE VIEW active_tagged_ids AS
SELECT DISTINCT t.unique_id
FROM tags t
JOIN terra_tag_config c ON t.tag = c.tag
UNION
SELECT DISTINCT u.unique_id
FROM user_tags u
JOIN terra_tag_config c ON u.tag = c.tag;
#+end_src

Then for each part table, create a filtered view:

#+begin_src sql
CREATE VIEW capacitors_smt_v AS
SELECT p.*
FROM capacitors_smt p
LEFT JOIN active_tagged_ids a ON a.unique_id = p.unique_id
WHERE p.tier <= (
        SELECT COALESCE(MAX(tier_level), 2)   -- default cutoff if empty
        FROM terra_tier_config
      )
   OR a.unique_id IS NOT NULL;
#+end_src

Important:
- If =terra_tag_config= is empty → =active_tagged_ids= is empty → tag path adds nothing.
- If =terra_tier_config= is empty → =COALESCE(..., 5)= ensures default tier cutoff.

*** Index Requirements (for performance)

The selection patterns require indexes in the “selection direction”:

- Tags (already defined above):
  - =tags(tag, unique_id)=
  - =user_tags(tag, unique_id)=

- Each part table should have:
  - an index on =(tier, unique_id)= (or at minimum =tier=), e.g.:

#+begin_src sql
CREATE INDEX IF NOT EXISTS idx_caps_smt_tier_uid ON capacitors_smt(tier, unique_id);
#+end_src

(If =unique_id= is the PRIMARY KEY, a separate =unique_id= index is unnecessary.)

** Generator Changes

*** All Generators

- Add =tier= and =tags= to INSERT column lists.
- Emit =INSERT INTO tags= statements for each part.
- Ensure tags are canonical: lowercase, hyphen-separated.

*** Yageo Resistor Generators (run_200, run_210)

Currently E24 and E96 values are unioned into a single set, losing
series origin. Change to:

1. Generate E24 values into a set.
2. Generate E96 values into a separate set.
3. For each value, determine tier:
   - If value is in E24 set → tier 3
   - If value is only in E96 set → tier 6
4. Union the sets for iteration, but carry the tier per value.

*** KEMET Cap Generator (run_300)

- All values are E24-based → tier 3.
- Tags: =passive=.

*** Samsung Cap Generator (run_400)

- All parts → tier 5 (catalog default).
- Tags: =passive=.

** Build System Changes

There are two build phases with different triggers.

*** Phase A: Master DB build (only when library changes)

Output: =db/terra_master.db=

Responsibilities:
1. Create all part tables and populate them.
2. Create =tags= and populate it (generator output).
3. Create the project-config tables *empty* (optional but recommended for schema consistency):
   - =terra_tier_config=
   - =terra_tag_config=
   - =user_tags=
4. Create =active_tagged_ids= view.
5. Create filtered views (=*_v=) for all part tables.
6. Create required indexes.

*** Phase B: Project DB build (per project; only when project config changes)

Output: =${KIPRJMOD}/terra_local.db=

Inputs (optional, may be missing):
- =${KIPRJMOD}/terra_config.sql=
- =${KIPRJMOD}/terra_tags.sql=

Algorithm:
1. Create =${KIPRJMOD}/terra_local.db= as a clone/copy of =db/terra_master.db=.
   - Linux: =cp --reflink=auto db/terra_master.db ${KIPRJMOD}/terra_local.db=
   - macOS (APFS): =cp -c db/terra_master.db ${KIPRJMOD}/terra_local.db=
   - fallback: normal copy
2. Apply default config *inside the project DB*:
   - ensure config tables exist (they should from the master clone)
   - set default tier cutoff row (e.g. 5)
   - clear active tags and user tags (empty by default)
3. If =terra_config.sql= exists, apply it (overrides defaults).
4. If =terra_tags.sql= exists, apply it (populates/overrides =user_tags=).
5. (Optional) Set WAL once for better read/write coexistence:
   - =PRAGMA journal_mode=WAL;=
6. Prefer atomic update to avoid KiCad reading a half-written DB:
   - write to =terra_local.db.tmp= then rename to =terra_local.db=.

*** Makefile Notes

- The master build target should not depend on project config files.
- Add a separate target to build the per-project DB, e.g.:
  =make project-db KIPRJMOD=/path/to/project=
- The .kicad_dbl generator should always reference =${KIPRJMOD}/terra_local.db=.

** HTTP Library Architecture (Preferred — Supersedes Copy/Modify Model)

The copy/modify model above (Phase B, project DB, config tables, SQL views)
is superseded by a lightweight HTTP server approach. The tier column, tags
column, and tags table remain useful as metadata for the server to filter on,
but KiCad no longer consumes the SQLite DB directly.

*** Why HTTP Libraries

KiCad 8+ supports HTTP libraries (=.kicad_httplib=) as an alternative to
ODBC-based =.kicad_dbl= files. A local server reads the master DB and serves
a REST API that KiCad queries for parts.

Advantages over the ODBC/copy model:

| Problem                        | ODBC model                          | HTTP model                          |
|--------------------------------+-------------------------------------+-------------------------------------|
| Filtering (tier, tags, mfr)    | Pre-built SQL views or pruned copy  | Server filters dynamically          |
| Per-project config             | Copy DB + apply SQL + prune         | JSON config file, no DB copy        |
| ODBC driver dependency         | Platform-specific driver install    | None — just HTTP                    |
| Discoverability                | Invisible parts, no search          | Web UI for browsing full catalog    |
| Upgrading master library       | Re-copy, re-apply config            | Symlink or share DB; restart server |
| Category granularity           | One table = one KiCad library       | Server splits into subcategories    |
| Composable filters             | One view per combination            | Server composes on the fly          |

*** Architecture

#+begin_src
Master DB (immutable, built by make)
    ↓
Terra Server (localhost, reads DB + project config)
    ↓  REST API
KiCad (just a .kicad_httplib pointing at localhost:PORT)
    ↑
Web UI (browse, search, tag — same server)
#+end_src

- Master DB is the single source of truth, built by =make= as today.
- Server reads the DB read-only. No copies, no clones, no ATTACH.
- Project config is a JSON file in =${KIPRJMOD}/terra.json=.
- KiCad sees a =.kicad_httplib= file, not a =.kicad_dbl=.
- The same server hosts a web UI for browsing and tagging.

*** KiCad HTTP Library API (v1)

KiCad expects these endpoints:

#+begin_src
GET /v1/categories.json              → [{id, name, description?}]
GET /v1/parts/category/{id}.json     → [{id, name, description?}]
GET /v1/parts/{id}.json              → {id, name, symbolIdStr, fields: {key: {value, visible?}}}
#+end_src

Category listing is fast (just names). Part listing within a category
returns only id/name/description. Full field data is fetched per-part
when the user clicks on it.

*Important*: KiCad fetches each part individually (N+1 pattern). The
mitigation is server-controlled category granularity — keep categories
small (50–200 parts).

*** .kicad_httplib Config

#+begin_src json
{
  "meta": {"version": 1.0},
  "name": "Terra EDA Library",
  "source": {
    "type": "REST_API",
    "api_version": "v1",
    "root_url": "http://localhost:8361/",
    "token": ""
  }
}
#+end_src

Placed in =${KIPRJMOD}/= or symlinked from =${TERRA_EDA_LIB}/=.

*** Project Config (=${KIPRJMOD}/terra.json=)

#+begin_src json
{
  "tier": 1,
  "include_tags": ["automotive", "low-noise"],
  "manufacturers": ["Yageo", "Samsung", "KEMET"],
  "hide_obsolete": true
}
#+end_src

- Git-trackable per project.
- Server watches or re-reads on request; KiCad sees changes on next
  category refresh.
- If absent, server uses sensible defaults (all tiers, no tag filter).

*** Dynamic Categories

The server builds categories from DB metadata. Instead of one flat
"resistors_smt" table with 20k parts, the server presents:

#+begin_src
SMT Resistors / 0402
SMT Resistors / 0603
SMT Resistors / 0603 / Thin Film
SMT Resistors / 0805
SMT Resistors / 1206
SMT Capacitors / X7R / 0402
SMT Capacitors / X7R / 0603
SMT Capacitors / C0G / 0603
...
#+end_src

Category tree is generated from columns like =package=, =dielectric=,
=tolerance=, etc. Each leaf category stays small enough (50–200 parts)
that the N+1 fetch pattern is tolerable over localhost.

*** Web UI

The same server provides a browser-based interface:

- Full-catalog browsing with search, filter, sort
- Datasheet links, parametric tables
- Per-project tagging: click to add/remove parts from project config
- Writes back to =${KIPRJMOD}/terra.json= (or uploads via the UI)
- Solves the discoverability problem — every part is visible and
  searchable regardless of what KiCad currently shows

*** Tier Column Under HTTP Model

Tiers are no longer load-bearing architecture. With server-controlled
categories, every part is reachable — just organized into subcategories.

The tier column remains useful as soft metadata:

- Category ordering: tier 0 parts sort to top within subcategories
- "Favorites" virtual category: cross-type collection of daily drivers
- Web UI: tier 0 expanded by default, higher tiers collapsed
- Default filtering: project config can still say ="tier": 1= to limit
  what KiCad sees, but it's optional rather than required for performance

*** Server Implementation

Lightweight Python server (FastAPI or Flask). Key components:

- SQLite read-only connection to master DB
- Category builder: queries distinct values from package/dielectric/type
  columns, builds hierarchical category tree
- Part serializer: maps DB columns to KiCad HTTP API field format
- Config loader: reads =${KIPRJMOD}/terra.json= for filtering
- Web UI: static HTML + JS for browsing/tagging (served by same process)

The server runs locally. Startup:

#+begin_src shell
terra-server --db /path/to/terra.db --project /path/to/project/
# or
terra-server --db ${TERRA_EDA_LIB}/db/terra.db --project ${KIPRJMOD}/
#+end_src

*** What Changes vs. ODBC Model

| Component                        | ODBC model (above)        | HTTP model                  |
|----------------------------------+---------------------------+-----------------------------|
| =terra_tier_config= table        | Needed                    | Removed (use terra.json)    |
| =terra_tag_config= table         | Needed                    | Removed (use terra.json)    |
| =user_tags= table                | Needed                    | Removed (use terra.json)    |
| =active_tagged_ids= view         | Needed                    | Removed                     |
| =*_v= filtered views             | Needed                    | Removed                     |
| =.kicad_dbl= files               | Primary integration       | Replaced by =.kicad_httplib= |
| =project-db= Makefile target     | Needed                    | Removed                     |
| ODBC driver                      | Required                  | Not needed                  |
| =tier= column                    | Hard filter               | Soft metadata               |
| =tags= column                    | Searched via SQL views    | Searched by server           |
| =tags= table                     | Joined in views           | Queried by server            |
| Master DB                        | Copied per project        | Shared read-only             |
| =tools/generate_kicad_dbl_files.py= | Generates =.kicad_dbl= | Generates =.kicad_httplib=   |
| New: =tools/terra_server.py=     | N/A                       | HTTP server + web UI         |

*** Open Questions

- *N+1 performance threshold*: Need to prototype and measure. How many
  parts per category before KiCad becomes sluggish over localhost HTTP?
  Target: validate with 50, 200, and 500 parts per category.

- *Server lifecycle*: Auto-start on KiCad launch? Systemd user service?
  Manual start? Tray icon?

- *Multi-project*: Can one server instance serve multiple projects with
  different configs? (Probably yes — route by port or path prefix.)

- *Offline/portable*: If the server isn't running, KiCad shows empty
  libraries. Acceptable? Or keep a =.kicad_dbl= fallback for offline use?
